Backup e importación entre clústeres

El backup captura solo configuración cifrada. El import es un único job duradero con snapshot y rollback total de base de datos e infraestructura. La infraestructura no viaja en el archivo: cada clúster la reconcilia con sus propios nodos.

1. Exportación

GET /api/v1/system/backup/export?password=<password>

{
  "version": 1,
  "salt": "<base64>",
  "payload": "<ciphertext base64>"
}

Cifrado con Fernet; la clave se deriva con PBKDF2-SHA256 (100.000 iteraciones y salt aleatorio). La contraseña nunca se guarda en el archivo ni en el servidor.

Los password_hash se restauran tal cual (ya hasheados con bcrypt). Los datos operativos y la infraestructura quedan fuera: cada clúster gestiona la suya mediante deploy.

2. Import: un solo job

POST /api/v1/system/backup/import
Content-Type: multipart/form-data

file:     <archivo cifrado>
password: <password>

HTTP/1.1 202 Accepted
{
  "ok": true,
  "message": "Backup importado. Reconciliando infraestructura de 3 tenant(s)…",
  "tenants_count": 3,
  "skipped": 1,
  "job_id": "<uuid>"
}
1
Parse, decrypt y validación. Si falla: 400 y ningún cambio.
2
Guard: si ya hay backup_import queued/running → 409.
3
En una transacción: snapshot de BACKUP_TABLES en backup_import_state, upsert por PK, _fix_sequences y plan de reconciliación con auto-placement.
4
Se encola un único job backup_import con created_by del usuario y timeout_at. Commit y respuesta 202.
El upsert no destruye: los registros existentes ausentes del backup no se borran. Solo se insertan columnas que realmente existen en la tabla (validación con information_schema), lo que evita inyección SQL desde el archivo.

3. Desacople de nodos y reconciliación

_detach_tenant_node_refs  (al importar)
  vmalert_node_id   -> NULL
  vmauth_node_id    -> NULL
  instance_id       -> NULL
  vmalert_port      -> NULL
  placement_mode    -> 'auto'

_job backup_import_
  vmalert_redeploy       encolado y esperado (900 s desde started_at)
  vmalert_regen_scrapes  encolado y esperado (300 s)
  parses_provision       directo en el hilo del orquestador
  steps[] y progress_pct publicados en job_state
parses_provision se ejecuta directo, no se encola: el ejecutor es serial y encolarlo lo pondría en la misma cola que el job que lo espera (deadlock). Los tenants internos se omiten del plan porque ya existen y no requieren reconciliación.

4. Rollback total

OrdenAcciónModo
1Para cada tenant nuevo: vmalert_undeploy y delete_tenant_parses.Best-effort, antes de tocar la BD
2restore_import_snapshot(job_id): borra PKs introducidas y re-upserta el snapshot.Transaccional
3vmalert_regen_scrapes global para retirar rutas huérfanas.Determinista

Un backup_import huérfano (proceso muerto a mitad) ejecuta el mismo rollback antes de marcarse failed. Si vence timeout_at también dispara rollback. El job sobrevive al vencimiento del token del navegador.

5. Seguimiento y reconexión

GET /api/v1/admin/jobs/{job_id}
{
  "type": "backup_import",
  "status": "running",
  "phase": "vmalert_redeploy",
  "progress_pct": 45,
  "steps": [
    {"name": "vmalert_redeploy", "status": "running"},
    {"name": "parses_provision", "status": "pending"}
  ]
}

GET /api/v1/admin/jobs?type=backup_import&limit=1

La última ruta permite reengancharse al import tras recargar la página o vencer el sondeo. Al terminar se borra la fila de backup_import_state y se emite la notificación al dueño.
