Alta y ciclo de vida de un tenant

El alta es 100% background, con el mismo patrón del import de backup: la request solo valida y persiste la intención, y un único job orquesta todas las fases. El endpoint responde de inmediato y el operador sigue el avance por sondeo, con reanudación tras recargar la página.

Permiso requerido: tenants_manager. La identidad del dueño del job se guarda en job_state.created_by para notificar el desenlace; los jobs internos de sistema llevan created_by = NULL y no notifican.

1. Contrato HTTP

POST /api/v1/admin/tenants
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "name": "tenant-ejemplo",
  "display_name": "Ten Ejemplo",
  "type": "metrics",
  "environment": "default",
  "has_alerts": true,
  "placement_mode": "auto",
  "vmauth_placement_mode": "auto"
}

HTTP/1.1 202 Accepted
{
  "status": "accepted",
  "message": "Creación de tenant en curso",
  "id": 42,
  "job_id": "<uuid>"
}

No se devuelve 201 y tampoco infraestructura lista en la respuesta. El código 202 es la señal de que el trabajo fue aceptado; el tenant nace en status='provisioning' y sigue así hasta la fase waiting_ready, cuando los sondeos confirman que la ingesta (y vmalert, si aplica) responden.

Corrección importante: el nombre, el slug, los IDs de cuenta/proyecto, los datasources y el nodo de destino los decide el worker, no el cliente. El payload solo expresa intención (auto o valores manuales permitidos).

2. El job tenant_create

Registro

job_state con id, type='tenant_create', ref_id=tenant_id, status='queued', phase='init', progress_pct=0 y created_by.

Durabilidad

timeout_at, heartbeat y recuperación de huérfanos (spec 016). Si el proceso muere, el job se marca failed y se reintenta/audita según su tipo.

Progreso

phase, progress_pct y steps[] con {name, status, detail?} publicados tras cada fase.

NOTIFY

Los cambios de estado llegan por NOTIFY de PostgreSQL; el sondeo HTTP sigue siendo la fuente de verdad para reconectar.

GET /api/v1/admin/jobs/{job_id}

{
  "id": "<uuid>",
  "type": "tenant_create",
  "ref_id": 42,
  "status": "running",
  "phase": "waiting_ready",
  "progress_pct": 96,
  "created_by": 7,
  "steps": [
    {"name": "assigning_ids", "status": "succeeded"},
    {"name": "seeding_datasources", "status": "succeeded"},
    {"name": "auto_placement", "status": "succeeded"},
    {"name": "activating", "status": "succeeded"},
    {"name": "deploying_vmalert", "status": "succeeded"},
    {"name": "regenerating_scrapes", "status": "succeeded"},
    {"name": "provisioning_parses", "status": "succeeded"},
    {"name": "waiting_ready", "status": "running"}
  ]
}

GET /api/v1/admin/jobs?type=tenant_create&limit=20
El listado GET /api/v1/admin/tenants expone vmalert_deployed, job_status, job_phase, job_progress y ready (status='active') para seguir el despliegue desde la UI; no usa campos vmalert_job_*.
Reanudación tras recarga: la UI no pierde el rastro. Al cargar busca jobs queued/running de este tipo con ref_id del tenant o por created_by, adopta el job_id y continúa el sondeo. El job vive en PostgreSQL, no en la pestaña ni en localStorage.
Notificación al dueño: al llegar a estado terminal, notify_job_outcome crea una notificación in-app para created_by (y email si hay SMTP configurado). El vencimiento del token del navegador no interrumpe el job.

3. Fases del pipeline

FaseAvanceQué ocurreFallido
assigning_ids15%El worker toma nextval de las secuencias y asigna account_id / project_id. Los tenants type='profiles' quedan en NULL.Aborta el job.
seeding_datasources30%Siembra tenant_datasources de forma idempotente desde los componentes select. Perfiles usa el datasource Pyroscope.Aborta el job.
auto_placement45%Elige nodo vmauth y nodo vmalert con menor carga si el modo es auto; contabiliza el slot del nodo vmauth.Aborta el job.
activating~50%El tenant sigue en status='provisioning': no se publica como activo hasta que terminen las fases dependientes y el healthcheck final.Aborta el job.
deploying_vmalert55% / 80%Si has_alerts=true y no es profiles: encola vmalert_deploy con skip_regen=True y espera su resultado (presupuesto 900 s desde started_at). El deploy asigna el puerto en remoto, espera /health y registra la instancia; durante la ventana se mantiene un silence planificado de VmalertTenantDown.Error de fase → rollback.
regenerating_scrapes82% / 84%Siempre se encola vmalert_regen_scrapes (300 s), con o sin vmalert, ya que el deploy no regenera por skip_regen. Materializa scrapes de vmagent y rutas de vmauth desde la BD, incluido el tenant en provisioning.Error de fase → rollback.
provisioning_parses85% / 95%Provisión dependiente de Parses: project anomalia-tenant-<slug>, datasources y, solo si es interno, dashboards. Se ejecuta dentro del thread del orquestador para no auto-bloquear el ejecutor serial.Propaga el error → rollback.
waiting_ready96%Sondea /health de ingesta, la ruta de ingesta según el tipo (/insert/loki/api/v1/push, /insert/opentelemetry/v1/traces o /insert/prometheus/api/v1/write) y /health de vmalert si aplica. Si responden, promueve el tenant a active y notifica el éxito; si no, rollback.Sin respuesta tras los intentos → rollback.
done100%Job succeeded, tenant activo y notificación al dueño.—
Dependencias, no fuego y olvido: vmalert_deploy, vmalert_regen_scrapes y la provisión de Parses son fases dependientes: se encolan o ejecutan y se esperan antes de continuar. El regen lo encola el orquestador (skip_regen=True en el deploy) y la fase waiting_ready hace el último sondeo HTTP. La espera mide el tiempo desde que el job dependiente arranca, con una gracia separada para el tiempo en cola (spec 016 §2.5).

4. Concesión de acceso: solo role_tenants

INSERT INTO role_tenants (role_id, tenant_id)
SELECT r.id, <tenant_id>
FROM roles r
WHERE r.name = 'admin'
  AND NOT EXISTS (
    SELECT 1 FROM role_tenants rt
    WHERE rt.role_id = r.id AND rt.tenant_id = <tenant_id>
  );

INSERT INTO role_tenants (role_id, tenant_id)
SELECT r.id, <tenant_id>
FROM roles r
WHERE r.name = 'tenant_manager'
  AND <environment> IN ('work', 'default')
  AND NOT EXISTS (
    SELECT 1 FROM role_tenants rt
    WHERE rt.role_id = r.id AND rt.tenant_id = <tenant_id>
  );
NUNCA insertar en user_tenants durante el alta. La concesión automática es para los roles admin y tenant_manager, y se registra únicamente en role_tenants. user_tenants es para asignaciones directas hechas desde el ABM de usuarios o aprobaciones (spec 007: unión user_tenants ∪ role_tenants).

La concesión es best-effort: un fallo no bloquea el alta, pero el access check posterior se resuelve desde la base, así que conviene verificar las filas antes de entregar el tenant.

5. Red, puertos y consolas

vmalert por tenant

Unit systemd derivada anomalia-vmalert-<slug>.service. El puerto se asigna en remoto con allocate-vmalert-port.yml (preferido, pool del nodo o cola libre) y la instancia solo se registra tras responder /health. Durante el mantenimiento se silencia VmalertTenantDown.

vmauth

El regen de scrapes/rutas se materializa con Ansible y vmauth se recarga o reinicia vía systemd. La ruta pública del tenant queda resuelta desde la BD; el cliente no elige nodo.

Dashboards

Solo internos. Los tenants is_internal=TRUE reciben dashboards nativos; un tenant nuevo arranca con project y datasources, sin dashboards heredados.

Acceso

HTTPS en el gateway; los puertos de lectura de Victoria están aislados. Las consolas se abren con tickets: ver tickets-workflow.html.

6. Rollback y trazabilidad

Ante un error en cualquier fase, _rollback_tenant_create hace limpieza best-effort y deja la fila del tenant en status='failed' para trazabilidad (la purga definitiva es una baja explícita).

AcciónModoDetalle
Liberar slot de vmauthDeterministatenants_count_active = GREATEST(tenants_count_active - 1, 0).
Mantenimiento vmalertDeterministaAbre un silence planificado de VmalertTenantDown y lo levanta al terminar; el undeploy del rollback usa skip_silence=True para no duplicarlo.
Quitar vmalertBest-effortEncola vmalert_undeploy y espera con timeout acotado; fallo se registra como warning.
Quitar ParsesBest-effortdelete_tenant_parses(tenant_id).
Regen de rutasBest-effortTras la limpieza encola vmalert_regen_scrapes para retirar scrapes y rutas del tenant; fallo se registra como warning.
Limpiar BDDeterministaBorra tenant_datasources y relaciones de acceso; fija status='failed'.
AuditoríaDeterministaInserta en audit_deletions con outcome='rolled_back' y un challenge_id único.
Rollback best-effort no significa "borrar el tenant": significa que el tenant queda marcado failed y auditado. No reintentar el alta sobre la misma fila sin revisar primero audit_deletions y el job original.

Verificación operativa

1
Confirmar 202, id y job_id; nunca esperar infra en la respuesta.
2
Sondear phase, progress_pct y steps[] hasta succeeded / failed.
3
Verificar account_id, project_id y tenant_datasources escritos por el worker.
4
Confirmar que solo hay filas nuevas en role_tenants y que user_tenants no fue tocado.
5
Cuando has_alerts, comprobar la unit vmalert, su puerto asignado por Ansible y los sondeos de waiting_ready antes de ver el tenant como active.
6
Confirmar la notificación in-app al dueño del job.
