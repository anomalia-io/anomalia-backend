Emisión, canje y sesión de tickets UI

El JWT vive en localStorage y no viaja en la navegación. Para abrir una consola se emite un ticket opaco con el JWT, se canjea una sola vez y se mantiene una cookie de sesión mientras la pestaña siga en uso.

Corrección de contrato: POST /api/v1/ui/ticket responde 200 OK, no 201. El cuerpo contiene únicamente {"url": "/ui/redeem/<ticket>"}.

1. Emisión

POST /api/v1/ui/ticket
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "tenant_id": 42,
  "scope": "metrics"
}

HTTP/1.1 200 OK
{ "url": "/ui/redeem/<ticket_opaco>" }
tenant_id es Optional[int]: es obligatorio para todos los scopes salvo alertmanager_global, que no tiene tenant. Si falta en un scope que lo requiere, la API devuelve 422.

Antes de emitir, el backend valida el JWT, resuelve el perfil exigido por el scope consultando la BD (user_roles → role_profiles → profiles), re-chequea la pertenencia al tenant (user_tenants ∪ role_tenants) y resuelve el upstream. Si el upstream no está listo, falla rápido y no entrega una URL que luego no sirva.

3. Canje, cookie y expiración deslizante

1
GET /ui/redeem/<ticket> es el único punto navegable sin credencial. Marca consumed_at y redirige con 307 al mount del scope.
2
Fija la cookie anomalia_ui=<ticket> con Path=/ui/<ticket>, Max-Age=1800, HttpOnly, SameSite=Lax y Secure solo si el request es HTTPS.
3
Cada petición válida al proxy renueva la vida del ticket cuando quedan menos de 15 minutos (TTL 30 min, umbral 15 min) y vuelve a escribir la cookie para que el navegador no la deseche antes de tiempo.
4
Las consolas de administración (vmalert, alertmanager_global) re-validan el perfil desde la BD en cada request.
No confundir: el uso único aplica al canje del ticket, no a la cookie. Después del canje, la cookie se reutiliza durante toda la sesión. La cookie no está cifrada: contiene el valor opaco del ticket, cuya vigencia y permisos se comprueban en el servidor.
No hay auditoría persistida de emisión ni canje en este flujo: solo se registra con logger. La tabla ui_tickets guarda estado operativo (ticket, usuario, tenant, scope, expiración, consumo), no una bitácora de auditoría. Para auditoría de acceso use los mecanismos del gateway.

4. Códigos de error

CódigoCausas en este flujo
400scope desconocido; ruta de UI inválida; perfil inexistente para una consola de administración.
401Token inválido o usuario inexistente; ticket inválido, expirado o ya usado; sesión de UI requerida.
403Sin perfil del scope; sin acceso al tenant; ticket de otro tenant; project de Parses ajeno; método de escritura no permitido en consolas de solo lectura.
404Tenant sin tenant_datasources de lectura; upstream o ruta API de Parses inexistente.
409Conflicto de estado del upstream (por ejemplo, vmalert del tenant aún no desplegado al resolver la consola).
422Falta tenant_id en un scope que lo requiere.
503No hay nodo disponible para resolver el upstream solicitado.
Un ticket expirado devuelve una página HTML legible si el navegador pidió el documento, o JSON si lo pidió un fetch de la propia consola. Así se evita el bucle de 401 que dejaba la consola en blanco.

Verificación rápida

1
POST con perfil insuficiente → 403; con scope inexistente → 400.
2
Canjear dos veces el mismo ticket → 401 en el segundo intento.
3
Reutilizar la cookie tras el canje → peticiones correctas y contador creciente.
4
Inactividad > 15 min → se renueva en la siguiente petición válida.
5
Cerrar la pestaña y dejar caducar → accesos con 401 y página legible.
