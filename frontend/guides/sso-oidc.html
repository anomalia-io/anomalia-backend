SSO con OIDC

El gateway puede autenticar con login local, OIDC o ambos. El proveedor activo se configura en system_settings y en oidc_providers; el flujo usa state, nonce y PKCE, y emite el JWT interno habitual al finalizar.

1. Modos de autenticación

GET /api/v1/settings/auth   (publico)
{ "auth_mode": "hybrid", "oidc_enabled": true, "local_enabled": true }

system_settings.auth_mode:
  local       login local si, OIDC no,  local_enabled = true
  local_only  login local si, OIDC no,  local_enabled = true
  hybrid      login local si, OIDC si,  local_enabled = true   (default)
  oidc_only   login local no, OIDC si,  local_enabled = false

La UI y la app móvil leen este resumen para mostrar u ocultar el formulario local y el botón OIDC. Solo se admite un proveedor activo: default_oidc_provider_id.

2. Flujo de autorización

1
GET /api/v1/oidc/login?session_type=web|mobile&provider_id=<id>&redirect_uri=.... Resuelve endpoints por discovery (con fallback manual), genera state, nonce y code_verifier con PKCE S256, y persiste la sesión.
2
El IdP redirige a /api/v1/oidc/callback?code=<code>&state=<state>. Ese es el redirect_uri registrado, no la página de aterrizaje.
3
Se valida state, se intercambia el código según client_auth_method con el code_verifier y se verifica el ID token: firma vía JWKS, iss, aud, exp con skew de 60 s y nonce.
4
Se aplican reglas de negocio y se emite un JWT interno con create_admin_access_token.
5
La respuesta depende de session_type: web → 302 a /auth/callback?token=...&username=...&role=...; mobile → JSON con access_token, token_type, username y role.
oidc_sessions
  id · state · nonce · code_verifier · redirect_uri · client_id
  provider_id · session_type (web|mobile) · expires_at · created_at

TTL de la sesion OIDC: 10 minutos, de un solo uso
Indices: idx_oidc_sessions_state, idx_oidc_sessions_expires

3. Auto-provisionamiento

ReglaComportamiento
Usuario nuevoSi oidc_auto_provision=true se crea activo, sin contraseña local usable.
Roles y tenantsNo se asignan por defecto. Solo si el IdP los envía en claims y el nombre coincide con un rol/tenant existente; alta aditiva con ON CONFLICT DO NOTHING.
Email verificadoSi oidc_require_email_verified=true y falta email_verified=true, se rechaza el login.
Dominiosallowed_domains (CSV) restringe el auto-provisionamiento por dominio del email.
IdentidadPrioridad: oidc_username_claim (default email) → email → preferred_username → sub.
Grupos → rolesFuera de alcance: no se mapean grupos automáticamente a roles/perfiles.
Un usuario aprovisionado por OIDC puede quedar sin permisos. Eso es intencional: otorgá roles y tenants desde el ABM o mediante el flujo de aprobaciones.

4. Configuración del proveedor

GET /api/v1/settings/sso      (admin, sin secretos)
PUT /api/v1/settings/sso      (admin)

discovery_url · authorization_endpoint · token_endpoint · jwks_uri
userinfo_endpoint · end_session_endpoint · scopes ("openid profile email")
use_discovery (true) · client_auth_method ("client_secret_basic")
pkce_enabled (true) · allowed_domains · default_roles (vacio)

GET|POST|PUT|DELETE /api/v1/oidc/providers
Las respuestas de configuración no devuelven client_secret: solo has_client_secret. El secreto se entrega por un canal seguro y nunca se escribe en inventarios, documentación ni respuestas de API.

5. Web y móvil

Web

login.html consulta /settings/auth. /auth/callback sirve una página mínima que guarda el token en localStorage y navega a la raíz. No procesa code ni state.

Flutter

El deep link anomalia://callback recibe code/state y la app llama al callback con session_type=mobile para completar el intercambio.

Verificación

1
El proveedor por defecto es único y el redirect_uri registrado apunta a /api/v1/oidc/callback.
2
Se validan state, nonce, firma JWKS, iss, aud y exp.
3
El usuario nuevo no recibe roles salvo claims explícitos y válidos.
4
El token devuelto es el JWT interno y funciona con los perfiles del backend.
